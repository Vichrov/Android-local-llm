# Local Eyes v0.5 — технический план

Рабочее название: **Performance · Living Eyes · Flyme**  
Целевая платформа: **Android 12+ (API 31+), ARM64, Snapdragon 855 и новее**.  
Главный принцип: приложение остаётся **локальным** — LLM, ASR, TTS-оркестрация, анимации, профили производительности и бенчмарки не требуют облачного сервиса и не отправляют пользовательские данные.

## 1. Цели релиза

v0.5 должен одновременно улучшить три области:

1. **Максимальная производительность** — уменьшить время до первого токена и увеличить скорость генерации без потери совместимости со Snapdragon 855.
2. **Живые глаза** — сделать глаза заметно естественнее, но сохранить минималистичный характер: никаких реалистичных зрачков, лиц, бровей или тяжёлых графических ресурсов.
3. **Flyme-дизайн** — довести весь интерфейс до единой визуальной системы, близкой по принципам к Flyme 12, не копируя проприетарные ресурсы Flyme.

Не является обязательной целью v0.5: управление Android-приложениями, долговременная память, облачные функции, постоянное фоновое прослушивание, обязательное GPU/NPU-ускорение на каждом устройстве.

---

## 2. Текущая архитектура и ограничения

На момент v0.4-1:

- UI — один `MainActivity` на Java/Android Views, без Compose;
- `MainActivity.java` одновременно содержит UI, состояние чата, переключение экранов, загрузку модели и координацию голоса;
- LLM — `NativeLlm.java` + JNI `bridge.cpp` + закреплённый llama.cpp;
- GGUF загружается через `mmap`;
- контекст — 2048 токенов;
- `n_batch = 128`, `n_ubatch = 128`;
- CPU-потоки — до 4;
- GPU сейчас отключён (`n_gpu_layers = 0`);
- KleidiAI сейчас отключён в CMake (`GGML_CPU_KLEIDIAI=OFF`);
- генерация ограничена 512 токенами;
- на каждом новом запросе KV-memory очищается и предыдущие обмены снова входят в prompt;
- JNI отправляет Java callback практически на каждый готовый токен/UTF-8-фрагмент;
- ASR: Vosk и GigaAM/Sherpa ONNX;
- TTS: Android `TextToSpeech`, выдача текста потоковыми фрагментами;
- `EyesView` — собственный Canvas View с двумя скруглёнными прямоугольниками, состояниями IDLE/LISTENING/THINKING/SPEAKING/ERROR, морганием и лёгким движением;
- тёмная/светлая темы уже следуют системной теме;
- релизный ABI — `arm64-v8a`; CI дополнительно собирает x86_64 для эмуляторов;
- minSdk 31, targetSdk 35.

### Архитектурное правило v0.5

Не переписывать приложение на Compose и не менять всё сразу. Разделить ответственность внутри существующей Java/Views-архитектуры, чтобы не сломать уже работающий голосовой тракт и жизненный цикл LLM.

# 3. Направление A — максимальная производительность

## A0. Сначала измерения, потом оптимизация

Добавить единый `PerformanceStats` / `InferenceStats` слой.

Измерять локально:

- время `llm.load()`;
- время tokenization/prefill;
- **TTFT** — time to first token;
- decode tokens/s;
- число prompt/generated tokens;
- выбранное число потоков;
- используемый backend: CPU / CPU KleidiAI / experimental OpenCL;
- доступную RAM перед загрузкой;
- PSS/RSS процесса после загрузки;
- thermal status Android;
- длительность текущей сессии генерации.

В UI показывать только компактный итог: `Первый токен 1.8 с · 7.4 ток/с · CPU`.
Подробные данные — отдельная карточка «Производительность» в настройках.

Телеметрия наружу не отправляется. При необходимости пользователь сможет вручную экспортировать текстовый benchmark report.

## A1. KleidiAI как основной CPU fast path

Текущий CMake отключает `GGML_CPU_KLEIDIAI`. В v0.5:

- включить KleidiAI **только для arm64-v8a**;
- для x86_64 CI оставить его отключённым;
- сохранить `GGML_NATIVE=OFF` для корректной cross-compilation;
- сохранить переносимый ARM baseline — не поднимать глобальный `-march` до armv8.6/8.7, чтобы не сломать Snapdragon 855;
- добавить native diagnostic flag, позволяющий проверить, какой CPU backend реально выбран llama.cpp;
- выполнить A/B benchmark обычного CPU backend и KleidiAI на одинаковой модели/промпте.

Критерий принятия: включение KleidiAI не должно ухудшать стабильность или ломать устройства без новых ARM-инструкций; несовместимые kernel path должны автоматически уходить в fallback.

## A2. Автоматический профиль потоков

Не закреплять «4 потока» как универсальный максимум.

Добавить `PerformanceProfile`:

- `AUTO` — по умолчанию;
- `ECO` — меньше потоков, меньше нагрев;
- `BALANCED`;
- `MAX` — максимум производительности в рамках безопасного лимита.

Для AUTO:

1. получить количество доступных CPU;
2. ограничить диапазон примерно 2–6 потоками;
3. на первом запуске конкретной модели выполнить короткий локальный micro-benchmark;
4. сравнить 2/4/(при наличии) 6 потоков на небольшом prefill/decode;
5. сохранить лучший вариант для пары `устройство + модель + quant`;
6. повторять калибровку после обновления inference engine или вручную.

Не использовать агрессивное повышение приоритета процесса. Worker thread может работать с `THREAD_PRIORITY_DEFAULT`/слегка повышенным приоритетом, но UI и аудио не должны голодать.

## A3. Batch/context tuning

Проверить профили:

- `n_batch`: 128 / 256;
- `n_ubatch`: 128 / 256;
- context: 1024 / 2048 / 4096 как advanced option.

2048 оставить дефолтом для Snapdragon 855+.

AUTO должен учитывать свободную RAM. Нельзя увеличивать контекст только ради маркетинговой цифры: при риске swap/LMK лучше оставить 2048.

## A4. Уменьшение JNI/UI overhead

Сейчас native callback создаёт `byte[]` и делает переход JNI на каждый готовый фрагмент.

Изменить поток вывода:

- собирать UTF-8 в native буфер;
- отправлять chunk при одном из условий: 20–35 мс прошло, накоплено >= 32–64 байт, завершено предложение, генерация закончена;
- UI обновлять максимум примерно 30 раз/с;
- TTS продолжает получать текст через существующий `VoiceOutput`, но не требует отдельного UI redraw на каждый токен.

Ожидаемый эффект: меньше JNI allocations, меньше `Handler.post`, меньше layout/text invalidation, более ровная генерация на слабых устройствах.

## A5. Conversation KV cache

Сейчас `llama_memory_clear()` выполняется перед каждым запросом, а последние обмены заново проходят prefill.

Для v0.5 спроектировать session-oriented native API:

- `newConversation()`;
- системный prompt загружается один раз;
- новые user/assistant tokens добавляются последовательно;
- KV cache сохраняется между ходами;
- при `Новый диалог`, смене модели или переполнении контекста cache очищается;
- при Stop/error незавершённый turn должен быть безопасно откатан или сессия должна пересобираться из Java history;
- при приближении к context limit — rebuild с короткой историей, а не crash.

Это должно прежде всего уменьшить TTFT во втором и последующих сообщениях.

## A6. Загрузка модели и память

Сохранить `mmap` как основной путь.

Добавить:

- реальный progress callback `llama_model_params.progress_callback` -> JNI -> UI, если upstream callback стабильно выдаёт прогресс;
- fallback на indeterminate animation, если процент недоступен;
- измерение фактического времени загрузки;
- сохранение модели загруженной при переходах Chat/Settings и смене системной темы;
- запрет двух одновременных load;
- явное освобождение старой модели до загрузки новой;
- защиту от LMK через проверку доступной RAM + запас.

Не использовать `mlock` по умолчанию: на Android это может ухудшить давление на память.

## A7. Experimental Adreno GPU

GPU не должен быть обязательным для v0.5.

Стратегия:

- baseline для Snapdragon 855/Adreno 640 — оптимизированный CPU;
- создать экспериментальный OpenCL backend;
- runtime probe: наличие OpenCL platform/device, Qualcomm vendor, успешная компиляция kernel и короткий inference self-test;
- только после успешного self-test показывать настройку `GPU (экспериментально)`;
- при любой ошибке автоматически fallback на CPU без падения приложения;
- хранить blacklist конкретного `SOC/driver` локально, если self-test упал;
- сравнивать TTFT, tokens/s и RAM с CPU перед тем, как рекомендовать GPU.

Причина осторожности: upstream llama.cpp поддерживает OpenCL для Adreno, но официально предупреждает, что старые A6xx GPU в телефонах могут иметь слишком старые драйверы/компиляторы. Поэтому нельзя обещать GPU-ускорение на Snapdragon 855.

### NPU

Hexagon/QNN считать отдельным research spike. Не делать NPU release blocker v0.5: сложность backend, зависимости и совместимость выше, чем у CPU/KleidiAI.

## A8. Thermal-aware поведение

Android `PowerManager` thermal status использовать только как защиту:

- `SEVERE+`: автоматически перейти из MAX в BALANCED/ECO после текущего токена/turn;
- показать ненавязчивое сообщение;
- не завершать диалог без необходимости;
- после нормализации температуры не повышать профиль мгновенно — cooldown.

Никаких скрытых «разгонов» CPU/GPU.

# 4. Направление B — живые глаза

## B1. Визуальный принцип

Глаза остаются двумя простыми цветными скруглёнными формами. Выразительность создаётся только:

- размером;
- высотой;
- расстоянием;
- вертикальным смещением;
- лёгким наклоном/асимметрией;
- цветом;
- скоростью движения;
- морганием.

Не добавлять реалистичные белки, радужку, зрачки, брови или лицо.

## B2. Новая state model

Отделить логическое состояние ассистента от параметров рисования.

`AssistantVisualState`:

- IDLE;
- LISTENING;
- HEARD / endpoint detected;
- LOADING_MODEL;
- THINKING;
- SPEAKING;
- HAPPY/SOFT_POSITIVE;
- ERROR;
- SLEEP/DIM при долгом бездействии.

Состояние конвертируется в набор числовых target-параметров, а `EyesView` только плавно интерполирует их.

## B3. Анимационный движок

Заменить `postInvalidateDelayed()` на `Choreographer`/vsync-driven rendering.

Режимы частоты:

- активное слушание/речь/переход — до 60 FPS;
- idle — 24–30 FPS;
- полностью статичное/невидимое состояние — 0 FPS;
- при системно отключённых анимациях — мгновенный переход и отсутствие постоянного redraw.

Цель: визуальная плавность без заметной нагрузки на CPU во время LLM inference.

## B4. Движения

Добавить минимальные поведенческие анимации:

- случайные micro-saccades в idle;
- редкие двойные моргания;
- мягкое «внимание» — глаза чуть шире при начале речи пользователя;
- listening — центрирование взгляда и реакция на RMS;
- endpoint — короткое подтверждение, что фраза услышана;
- thinking — едва заметная асимметрия/перекат;
- speaking — спокойная ритмика, не синхронизация «рот-в-рот»;
- error — краткий squash + переход в спокойный error color;
- model loading — медленный breathing pattern.

Случайность должна быть ограничена и детерминирована достаточно, чтобы глаза не выглядели нервными.

## B5. Реакция на контент

Текущая keyword-эвристика `рад/отлично/жаль/ошиб` слишком грубая.

В v0.5:

- не запускать отдельную emotion model;
- использовать только дешёвые локальные сигналы: punctuation, системное состояние, завершение/ошибка, тип ответа;
- максимум 2–3 мягких mood states;
- emotion никогда не должна менять смысл текста или работу LLM.

## B6. Performance budget EyesView

- никаких bitmap/frame animation;
- никаких allocations в основном `onDraw` цикле;
- один Paint/RectF и заранее подготовленные параметры;
- среднее время draw на целевых устройствах < 1–2 мс;
- idle animation не должна заметно влиять на tokens/s;
- full-screen eyes должны автоматически останавливаться, когда Activity не foreground.

# 5. Направление C — Flyme-дизайн

## C1. Дизайн-система вместо набора ручных значений

Не переходя на Compose, вынести tokens:

- размеры заголовков;
- body/caption typography;
- радиусы 14/18/24 dp;
- стандартные отступы 8/12/16/20/24;
- высоту контролов 48/52/56 dp;
- цвета surface/page/control/accent;
- disabled alpha;
- стандартные duration/easing.

Создать `UiTokens` / `UiFactory`, чтобы `MainActivity` не задавал стиль каждой кнопки вручную.

## C2. Декомпозиция MainActivity

Без изменения single-Activity lifecycle вынести:

- `ChatUi` — построение/обновление экрана чата;
- `SettingsUi` — модели и голос;
- `PerformanceUi` — метрики и профиль;
- `UiFactory` — кнопки, карточки, заголовки, переключатели;
- `AssistantController` — turn/busy/load state;
- `VoiceController` оставить поверх существующих HandsFreeVoice/VoiceOutput, не переписывая ASR без необходимости.

Цель: `MainActivity` становится coordinator, а не 40+ KB UI-файлом.

## C3. Иконка приложения

Использовать утверждённую минималистичную иконку Local Eyes в следующих релизах.

Подготовить Android resources:

- adaptive icon foreground;
- background layer;
- legacy mipmap PNG;
- round icon;
- monochrome layer для Android 13+ themed icons;
- safe zone, чтобы символ не обрезался разными launcher masks.

Не помещать название приложения внутрь иконки.

## C4. Экран чата

Цель — меньше визуального шума.

- крупный заголовок;
- одна основная карточка ответа;
- поле ввода и основные действия внизу;
- `Модели` и `Только глаза` — компактные secondary actions;
- auto-voice status не должен занимать несколько строк без необходимости;
- технические метрики скрыты по умолчанию и показываются по tap/в Performance section;
- при клавиатуре интерфейс должен естественно переходить в compact mode.

## C5. Экран моделей

Карточка модели должна показывать только:

- название;
- quant/размер;
- краткую рекомендацию;
- status;
- основное действие.

RAM estimate, backend и benchmark — раскрываемая техническая строка, чтобы основной экран не превращался в диагностическую панель.

## C6. Motion

Короткие Flyme-like transitions:

- 160–220 мс;
- fade + небольшое scale/translation;
- без overshoot/bounce;
- системный `Animator duration scale = 0` полностью отключает декоративную анимацию;
- model loading animation и eyes используют общую motion philosophy.

## C7. Темы

Сохранить автоматическое следование системной светлой/тёмной теме.

Не включать Material You dynamic color по умолчанию: фирменный синий Local Eyes должен оставаться стабильным. В будущем dynamic color можно сделать отдельной опцией.

# 8. Метрики успеха v0.5

Обязательные release gates:

- crash-free CI startup на API31/API35;
- отсутствие регрессии Vosk/GigaAM;
- отсутствие зависшего model-loading overlay;
- CPU backend работает на Snapdragon 855-class ARMv8 без требования новых ISA;
- при неподдерживаемом GPU приложение полностью работает на CPU;
- смена темы не выгружает модель;
- hidden/background EyesView не продолжает постоянный redraw;
- локальность и приватность v0.4 сохраняются.

Performance targets, а не жёсткие обещания:

- **+10–20% decode tokens/s** на поддерживаемых CPU paths либо эквивалентное снижение энергозатрат;
- **-15–30% TTFT** на втором и последующих turn благодаря KV/session cache;
- UI token streaming без заметного jank;
- рост RAM после оптимизаций — не более ~10% относительно сопоставимого v0.4-1 сценария;
- Eyes animation не должна снижать decode speed более чем на несколько процентов.

Если конкретная оптимизация не достигает измеримого выигрыша — не включать её только ради наличия функции.

# 9. Риски

### KleidiAI

Риск: разный выигрыш на старых/новых ARM cores и разных quant.  
Митигировать A/B benchmark и runtime fallback.

### OpenCL / Adreno

Риск: драйверы A6xx на старых телефонах.  
Митигировать self-test, feature flag, blacklist и CPU fallback.

### KV cache

Риск: рассинхронизация Java history и native context после Stop/error.  
Митигировать turn IDs, transaction-like commit turn и полный rebuild fallback.

### UI refactor

Риск: поломка lifecycle микрофона/LLM.  
Митигировать сохранением single Activity и поэтапным переносом экранов без переписывания voice stack.

### Eyes

Риск: лишняя нагрузка во время inference.  
Митигировать Choreographer, adaptive FPS и zero redraw вне foreground.
